## 1. プロジェクト概要

### 1.1 目的

保育園の持ち物・在庫管理、日常のTODO、ゴミ出しスケジュールを1つのアプリに集約し、家庭内の準備や日々のタスク管理を効率化する。

個人利用を主目的とし、実際に日常生活で使いながら段階的に機能を改善する。

また、本プロジェクトを通じて、AIエージェントを活用したWebアプリ開発、Gitによるソース管理、CI/CDパイプラインの構築と運用を学習する。

### 1.2 対象プラットフォーム

- iPhone向けWebアプリケーション
- iOSのSafariで利用できること
- ホーム画面に追加してアプリのように起動できるPWAを目指す
- Android向けの最適化は対象外
- PC向けの専用UIは対象外とする。ただし開発・保守時のPCブラウザ利用は妨げない

### 1.3 基本方針

- モダンでシンプルなUIとする
- 余計なキャッチコピーや装飾を設けない
- 日常的に使う機能へ少ない操作でアクセスできることを重視する
- 初期リリースでは必要最小限の機能に絞る
- 将来の機能追加を考慮し、保守しやすい構成とする
- AIエージェントによる実装を前提とし、仕様・設計・開発ルールをドキュメントとして管理する

### 1.4 日付の基準

- 「今日」「当日」「次回」などの日付判定は、すべて日本時間（Asia/Tokyo）で行う
- 端末やサーバーのタイムゾーン設定に依存しない実装とする

## 2. 画面構成

### 2.1 共通ナビゲーション

画面下部に固定フッターを設け、以下の4タブを表示する。

1. ホーム
2. 園ストック（仮称）
3. TODO
4. ゴミ出し

「園ストック」は、保育園に置いてある用品の在庫と、当日持参する用品を管理する画面を指す。

### 2.2 画面遷移

- タブ切り替え時にページ全体を再読み込みしない
- タブ切り替え後も、必要に応じて入力中の内容や状態を保持する
- 画面下部のナビゲーションは各画面で共通とする
- GitHub Pagesで公開するため、ページを再読み込みしたりURLを直接開いたりしても404にならないルーティング方式とする（方式は技術設計時に決定）

### 2.3 ログイン画面

- 未ログイン時は、ログイン画面のみを表示する
- ログイン画面には「Googleでログイン」ボタンを1つだけ置く
- ログイン後はホーム画面を表示する
- ログアウトの操作をどこかの画面に用意する（配置は技術設計時に決定）

### 2.4 ホーム画面

アプリ起動時に、当日確認すべき情報をまとめて表示する。

表示項目：

- 今日の日付
- 今日持参する保育園用品と持参数
- 未完了のTODO
- 次回のゴミ出し予定

各項目から対応する管理画面へ移動できること。

情報を一覧できることを優先し、詳細な編集操作は各機能の画面で行う。

## 3. 機能要件：保育園用品・在庫管理

### 3.1 目的

保育園に置いておく用品について、必要な数量、現在の園在庫、当日持参する数量を管理する。

### 3.2 管理対象の例

- 洋服
- エプロン
- タオル
- その他、任意に登録した用品

用品の種類や名称は固定せず、利用者が自由に登録できること。

### 3.3 用品情報

各用品について、以下の情報を保存する。

- 用品名
- 園に置いておく必要数
- 現在の園在庫数
- 表示順
- 登録状態（管理対象か、除外済みか）

数量は0以上の整数とする。

推奨持参数は保存せず、表示のたびに必要数と園在庫数から計算する。実際に持参した数量は、持参記録（3.6）として保存する。

### 3.4 園在庫と持参数の計算

当日の推奨持参数は、必要数と現在の園在庫数から自動計算する。

計算式：

推奨持参数 = max(0, 園に置いておく必要数 - 現在の園在庫数)

例：

- 必要数：5枚
- 現在の園在庫：3枚
- 当日の推奨持参数：2枚

現在の園在庫数が必要数以上であれば、推奨持参数は0枚とする。

利用者が推奨持参数を手動で変更できること。実際の持参数が推奨数と異なる場合にも対応できるようにする。

計算ロジックは画面から独立した関数として実装し、自動テストを設ける。

### 3.5 持参画面

登録済みの用品を一覧表示し、各用品について次の情報を確認できること。

- 用品名
- 必要数
- 現在の園在庫数
- 推奨持参数
- 実際に持っていく数量

実際に持参する数量は、用品ごとに編集できること。

持参数の初期値には、推奨持参数を設定する。

### 3.6 持参の一括記録

各用品の持参数を入力・確認した後、画面下部の「持参を記録」ボタンから一括確定する。

要件：

- 用品ごとに個別保存する方式ではなく、全用品をまとめて確定する
- ボタンを押す前は、各用品の持参数を編集できる
- 保存前に内容を確認できること
- 確定時に、各用品の実際の持参数を園在庫数へ加算する
- その日の持参記録（日付、用品ごとの持参数）を保存する
- 確定後は、記録が完了したことを画面上で明示する
- 二重タップや再読み込み等によって、同じ持参記録が重複して加算されないようにする
- 一括保存に失敗した場合は、その旨を表示し、在庫が一部だけ更新された状態を防ぐ

実装上の要件：

- 在庫の加算と持参記録の保存は、データベース側の1つのトランザクションで行う（例：SupabaseのRPC関数）
- 重複防止は画面側のボタン無効化だけに頼らず、データベース側でも防ぐ

一括記録の例：

記録前：
- エプロン：園在庫3枚、持参数2枚
- タオル：園在庫4枚、持参数1枚

一括記録後：
- エプロン：園在庫5枚
- タオル：園在庫5枚

### 3.7 園在庫の調整

持参記録とは別に、実際の園在庫数を手動で調整できること。

保育園から持ち帰った使用済み用品や、数量の数え違いなどを反映できるようにする。

初期リリースでは、複雑な在庫履歴や自動的な消費量推定は対象外とし、現在の園在庫を正しく管理することを優先する。

### 3.8 用品の管理

以下の操作を提供する。

- 用品の追加
- 用品名の変更
- 必要数の変更
- 園在庫数の調整
- 用品の表示順変更
- 用品の削除または管理対象からの除外

削除操作では、誤操作を防ぐため確認を設ける。

持参記録が残っている用品は、記録との整合性を保つため、物理削除ではなく管理対象からの除外を基本とする。

## 4. 機能要件：TODO

### 4.1 目的

保育園の通常の持ち物とは別に発生する用事や、日常の買い物などを簡易的に管理する。

### 4.2 登録内容

TODOには、以下の情報を持たせる。

- タイトル（必須）
- カテゴリ
- 期限（日付、任意）
- 完了状態
- 登録日時

カテゴリは、初期値として以下を用意する。

- 保育園
- 買い物
- その他

例：

- おむつを持っていく
- 袋を持っていく
- 牛乳を買う
- 書類を提出する

### 4.3 操作・表示

- TODOの追加
- TODOの編集
- TODOの削除
- 完了・未完了の切り替え
- 未完了TODOの優先表示
- 完了済みTODOの確認

期限が設定されている場合は、期限を表示する。

ホーム画面には未完了TODOを表示する。

### 4.4 初期リリースの対象外

- 複雑な優先度管理
- 繰り返しTODO
- 高度なフィルタリング
- TODO間の依存関係管理
- カテゴリの追加・編集（初期の3種類で固定）

## 5. 機能要件：ゴミ出しカレンダー

### 5.1 目的

地域のゴミ収集スケジュールを登録し、カレンダーや一覧から次回のゴミ出し予定を確認できるようにする。

### 5.2 ゴミの種類

ゴミの種類は利用者が自由に登録・編集できること。

例：

- 燃えるゴミ
- 燃えないゴミ
- 資源ゴミ
- プラスチック

初期状態で設定例を提供してもよいが、特定地域の収集ルールを固定しない。

### 5.3 スケジュール設定

以下の形式で収集スケジュールを登録できること。

1. 毎週の曜日指定
   - 例：毎週火曜日
2. 毎月の日付指定
   - 例：毎月15日
3. 毎月第N曜日指定
   - 例：毎月第2火曜日
4. 単発の予定
   - 例：臨時収集や通常スケジュールとは異なる日程

各スケジュールには、対象のゴミの種類を設定できること。

### 5.4 カレンダー表示

- 月単位でカレンダーを表示する
- 収集日には、対象のゴミの種類がわかるようにする
- 日付を選択して、その日の収集予定を確認できる
- 次回の収集予定を一覧で確認できる
- ホーム画面にも次回の収集予定を表示する

### 5.5 日付計算

- 毎月第N曜日などの繰り返し予定を自動計算する
- 収集日が存在しない月（例：31日、第5火曜日）は、不存在の日付を誤って収集日として扱わない
- 月や年をまたいでも正しく次回収集日を計算する
- 日付計算ロジックは画面から独立した関数として実装し、自動テストを設ける

### 5.6 予定の修正

収集スケジュールを登録・編集・削除できること。

年末年始や祝日などによる例外日程については、初期リリースでは利用者が手動で調整する方式とする。

自治体の収集日情報を自動取得する機能は対象外とする。

### 5.7 リマインダー

将来的に、収集日の前日や当日に通知を送れるようにする。

通知タイミングの候補：

- 前日の夜
- 当日の朝

ただし、プッシュ通知機能は初期リリースの必須要件には含めず、カレンダー表示・次回予定表示を先に完成させる。

通知機能を追加する際には、iOSのPWA制約や通知送信の仕組みを踏まえて方式を検討する。

## 6. UI・UX要件

### 6.1 デザイン方針

- モダンでシンプルなデザイン
- 装飾よりも視認性と操作性を優先する
- 不要なキャッチコピーや説明文を画面に表示しない
- 色やアイコンは用途を理解するために必要な範囲で使用する
- iPhoneの縦画面を前提に設計する

### 6.2 操作性

- 片手でも操作しやすいボタンサイズと配置にする
- 固定フッターとコンテンツが重ならないようにする
- iPhoneのセーフエリアを考慮する
- 数量入力は編集しやすいUIにする
- 保存成功・失敗を利用者にわかるように伝える
- 重要な操作では、二重登録や誤削除を防ぐ

### 6.3 レスポンシブ対応

iPhoneでの利用を最優先とし、異なるiPhoneの画面サイズでもレイアウトが崩れないこと。

PCブラウザでも、開発時の操作や確認ができる程度には表示できること。

## 7. データ管理・バックエンド要件

### 7.1 基本方針

アプリのデータは、端末内だけではなくクラウド上（Supabase）に保存する。

iPhoneの機種変更やブラウザのデータ消去後も、ログインすれば保存データを復元できること。

### 7.2 データベース

SupabaseのPostgreSQLを利用して、以下のデータを管理する。

- 保育園用品（園在庫数を含む）
- 持参記録
- TODO
- ゴミの種類
- ゴミ出しスケジュール

最終的なテーブル設計は、各機能の振る舞いを確定した後に決定し、`docs/` 配下に記載する。

### 7.3 認証

- 認証方式は **Googleログインのみ** とする（Supabase Auth + Google OAuth）
- メール/パスワードなど、その他のログイン方式は無効にする
- Google CloudのOAuth同意画面は「テスト」状態で運用し、テストユーザーに登録したGoogleアカウントだけがログインできるようにする
- iPhoneのホーム画面アプリ（PWA）でGoogleログインが正常に動作しない場合は、メールで届く確認コードによるログイン（Supabaseのメール OTP）を予備として追加する

### 7.4 アクセス制御

- 全テーブルでRLS（行単位のアクセス制御）を有効にし、ログインした本人のデータだけを読み書きできるようにする
- テーブルは自動では公開されない設定のため、テーブル作成時には必要な権限付与（GRANT）とRLSポリシーを必ずセットで定義する
- ブラウザからアクセスされるクライアントコードに、secret key（旧service_role key）を含めない

### 7.5 データベースの変更管理

- テーブルや関数の作成・変更は、Supabase CLIのマイグレーションファイルとしてリポジトリで管理する
- 管理画面からの手作業によるスキーマ変更は行わない

## 8. 技術スタック

古い技術や保守性の低い構成は避け、一般的なドキュメントやコミュニティ情報を参照しやすい技術を優先する。

### 8.1 フロントエンド

- React
- TypeScript
- Vite（`base` は `/ouchi-board/`）
- CSS（具体的なスタイリング方式は技術設計時に決定）
- PWA対応

タブ切り替えによるページ全体の再読み込みを避けるため、SPA構成を採用する。

### 8.2 バックエンド・データベース

- Supabase（リージョン：Tokyo、無料プラン）
- PostgreSQL
- Supabase Auth（Googleログイン）
- Supabase CLI（マイグレーション管理）

アプリの規模に対して不要な独自バックエンドサーバーは設けない方針とする。

### 8.3 ソース管理・CI/CD

- GitHubでソースコードを管理する（公開リポジトリ）
- GitHub Issuesで作業単位を管理する
- GitHub Pull Requestsで変更をレビューする
- GitHub ActionsでCI/CDパイプラインを構築する

### 8.4 ホスティング

- GitHub Pagesを使用する（デプロイ元：GitHub Actions）
- 本番URL：https://ryoga-b.github.io/ouchi-board/

### 8.5 環境変数

| 変数名 | 内容 | 設定場所 |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | SupabaseのProject URL | ローカルの `.env`、GitHub Actions Secrets |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Supabaseのpublishable key | ローカルの `.env`、GitHub Actions Secrets |

- `VITE_` で始まる値はビルド後のファイルに含まれ、誰でも読める前提で扱う
- `.env` はコミットしない。値を空にした `.env.example` をコミットする
- secret keyやGoogleのクライアントシークレットは、リポジトリにもクライアントにも置かない

### 8.6 AIエージェント

Claude Codeを主な実装支援ツールとして使用する。

AIエージェントには、要件・設計・開発ルールを参照させ、作業単位ごとに実装・テスト・変更内容の説明を行わせる。開発ルールはリポジトリ直下の `CLAUDE.md` に記載する。

## 9. 非機能要件

### 9.1 保守性

- TypeScriptを利用する
- 機能ごとの責務を分離する
- 巨大なコンポーネントへの過度な集約を避ける
- 共通UIや共通ロジックは再利用できる構造にする
- データモデルと主要な設計方針をドキュメントに記載する

### 9.2 データの正確性

- 数量は0以上の整数とし、画面とデータベースの両方で制約をかける
- 持参数計算と日付計算を独立したロジックとして実装する
- 二重登録や二重加算を防ぐ
- 保存処理が失敗した際に、成功したように見せない
- 重要な計算ロジックには自動テストを設ける

### 9.3 セキュリティ

- Supabaseのアクセス制御（RLS）を適切に設定する
- クライアントに秘密情報を埋め込まない
- 公開リポジトリに個人情報や秘密情報をコミットしない
- 環境変数やデプロイ設定に含める値の公開可否を確認する（8.5）

### 9.4 パフォーマンス

- 日常利用で待ち時間が気にならないこと
- タブ切り替え時にページ全体を再読み込みしない
- 必要以上に複雑な構成や依存ライブラリを導入しない

### 9.5 運用コスト

- 初期段階では無料枠を優先する
- 利用規模に対して過剰なインフラを使用しない
- Supabaseの無料プランは、一定期間利用がないとプロジェクトが一時停止される場合がある。アプリが急に動かなくなった場合は、まず管理画面でプロジェクトの状態を確認する

## 10. GitHubを利用した開発フロー

### 10.1 基本フロー

1. GitHub Issueに作業内容と完了条件を記載する
2. 作業用ブランチを作成する
3. Claude Codeで実装する
4. 自動テスト・型チェック・Lint・ビルドを実行する
5. Pull Requestを作成する
6. 変更内容とCI結果を確認する
7. 問題がなければmainブランチへマージする
8. mainへのマージを契機に本番環境へ自動デプロイする

### 10.2 初期CI要件

Pull Request作成時および更新時に、以下を自動実行する。

- 依存関係のインストール
- Lint
- TypeScriptの型チェック
- 自動テスト
- プロダクションビルド

いずれかが失敗した場合は、失敗内容を確認できるようにする。

CIが動作するようになったら、mainブランチを保護し、Pull Request経由のマージとCI成功を必須にする。

### 10.3 初期CD要件

mainブランチへのマージを契機に、GitHub Actionsでビルドし、GitHub Pagesへ自動デプロイする。

- ビルド時の環境変数はGitHub Actions Secretsから渡す
- ビルドが成功した成果物をデプロイする
- デプロイ結果をGitHubのActions画面で確認できるようにする

### 10.4 段階的な拡張

初期リリースでは単純な開発・デプロイフローを優先する。

その後、必要に応じて以下を学習・導入する。

- 開発環境と本番環境の分離
- プレビュー環境
- デプロイ前の手動承認
- E2Eテスト
- デプロイ失敗時の復旧手順

## 11. 実装の進め方

以下の順で実装する。各段階は1つ以上のIssueに分け、Pull Request単位で進める。

1. **基盤**：Vite＋React＋TypeScriptの初期構成、CLAUDE.md、CI（Lint・型チェック・テスト・ビルド）、GitHub Pagesへのデプロイ
2. **ログイン確認**：Googleログインボタンだけの画面を公開し、iPhoneのSafariとホーム画面アプリの両方でログインできることを確認する
3. **共通レイアウト**：4タブの固定フッター、セーフエリア対応、PWA設定
4. **TODO**：最も単純な機能で、テーブル作成・RLS・画面実装の流れを確立する
5. **園ストック**：持参数計算（テスト付き）、一括記録のRPC関数
6. **ゴミ出し**：日付計算（テスト付き）、カレンダー表示
7. **ホーム**：各機能の情報を集約して表示する

## 12. 初期リリース対象外

以下は初期リリースには含めない。

- 写真からのOCRによるゴミ出しスケジュール登録
- 自治体の収集日情報の自動取得
- ゴミ出しのプッシュ通知
- 家族間のアカウント共有
- 複雑な園在庫履歴・分析機能
- 高度なTODO機能
- オフラインでのデータ変更と自動同期
- Android向けの最適化
- Googleログイン以外のログイン方式（7.3の予備方式を除く）

利用を通じて必要性が明らかになった場合、別途Issueとして追加する。

## 13. 初期リリースの受け入れ条件

### ログイン

- Googleログインでアプリに入れる
- テストユーザーに登録していないGoogleアカウントではログインできない
- iPhoneのホーム画面アプリからログインできる
- アプリを閉じて開き直しても、ログイン状態が保たれる
- ログアウトできる

### ホーム

- 今日の保育園持参数、未完了TODO、次回のゴミ出し予定を確認できる
- 4タブを切り替えてもページ全体が再読み込みされない

### 園ストック

- 用品を自由に登録できる
- 必要数と現在の園在庫を設定できる
- 推奨持参数が自動計算される
- 持参数を用品ごとに編集できる
- 全用品の持参数を最後に一括確定できる
- 確定後に園在庫が正しく更新される
- 同じ記録の二重加算が発生しない
- 在庫数を手動で調整できる

### TODO

- TODOの追加・編集・削除ができる
- 完了・未完了を切り替えられる
- 未完了TODOを確認できる

### ゴミ出し

- 週次、毎月の日付、毎月第N曜日、単発の予定を登録できる
- カレンダーで収集予定を確認できる
- 次回収集予定を確認できる
- 月をまたいだ日付計算が正しい

### データ保存・デプロイ

- 保存したデータがブラウザを閉じても保持される
- 認証した利用者以外がデータを参照・変更できない
- Pull RequestでCIが動作する
- mainブランチへのマージで自動デプロイされる
